I reviewed the Makefile shutdown correction again with those concerns in mind.

The original `make stop` target sent SIGTERM to the managed pipeline and dashboard processes but returned immediately. SIGTERM requests graceful termination; it does not guarantee that a process has already exited when the command returns. That created a small but real risk that child processes could remain alive after `make stop` completed.

The revised logic preserves SIGTERM as the normal shutdown mechanism. After sending SIGTERM, it waits for a bounded period while checking whether the managed processes have exited. In the normal case, the processes terminate during that interval and no additional signal is sent. SIGKILL is used only as a fallback if a managed process is still alive after the grace period.

The change is limited to the existing `stop` behavior. It does not alter pipeline execution, dashboard startup, tests, Docker commands, or other existing Makefile targets.

I also checked the commands used by the shutdown logic. They rely only on standard process-management behavior already used by the project rather than adding a new runtime dependency or service. No additional container infrastructure is required.

I agree that the port 8501 conflict is environmental. It was caused by another container already binding that host port, so I did not change docker-compose.yml or the documented default port. Changing the project to accommodate an unrelated local conflict would not be justified.
